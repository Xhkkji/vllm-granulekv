近三周 KVCache 工作进度汇报

汇报范围：2026 年 10 月 8 日至 27 日

数据截至：2026 年 10 月 26 日

一、目标与阶段进展

本阶段的目标是在单机单卡上，让长上下文 KV 不必全部常驻显存：SSD 保存历史，CPU 内存承接完整 KV，GPU 只保留计算需要的工作集，再通过稀疏选择和分层预取减少关键路径上的搬运。

与三周前主要打通恢复链路相比，现在已经补齐“读取历史、稀疏计算、保存新增 KV、再次恢复”的闭环，并从 32K 推进到 128K 定向正确性验证，探索了 512K 的运行边界。

10 月上中旬：核对恢复数据与计算结果，补齐新增 KV 的 CPU 备份和 SSD 保存，从“能读能算”推进到请求结束后数据仍可复用。

数据组织优化：同层同 block 的 K/V 配对合并，由两个 16 KiB 片段改为一个 32 KiB SSD descriptor。相同 KV 数据量下，descriptor 数量减半，减少提交和完成处理开销。

10 月下旬前半段：已缓存历史和新生成历史统一参与稀疏选择；各层独立管理驻留数据，避免生成历史被整段搬回，减少层间覆盖引起的重复搬运。

10 月 25 日：GPU 工作集与逻辑上下文长度解耦，缩小评分临时空间，使历史继续增长时 GPU KV 区可以保持固定容量。

10 月 26 日：调度统一为四层窗口，对齐 Dense/Sparse 新增 KV 写回，补接 CPU READY 后的预测搬运，开始用相同保存义务比较性能，并定位预取尚未生效的环节。

二、当前链路实现了什么

当前沿用 SolidAttention-style 稀疏选择，参考 Tutti 的分层预取思路；这是本系统内的实现与对照，不是两篇论文的全量复现。

（1）历史数据读取：首个四层窗口的初选 KV 从 SSD 直接进入 GPU，其余历史从 SSD 进入 CPU，保留完整数据副本。

（2）计算按需取数：GPU 中的有效 KV 直接复用，缺失的选中 KV 从 CPU 传入 GPU；预测未覆盖的数据按实际选择补取。

（3）新增数据保存：新增 KV 按 GPU → CPU → SSD 的路径保存，已有有效 SSD 副本继续复用。

（4）窗口预取目标：计算当前四层，同时准备下一组四层；到边界再等待尚未就绪的数据。

CPU 保存完整历史，Attention 仍逐层只消费稀疏选择集合。四层是逻辑调度单位，目前不代表四层数据已合成一笔连续物理传输。

数据组织上，已将同一层、同一逻辑 block 的 K/V 连续配对，以一个 32 KiB descriptor 读写，替代原先分别描述 K 和 V 的两个 16 KiB 片段。这项优化不减少 KV 字节数，而是减少 I/O 描述与处理次数；32 KiB 指 KV 数据传输粒度，不是评分元数据大小，也不等于四层物理聚合。

Dense 对照保留 SSD→GPU 的历史直读，新生成 KV 同样经 CPU 写回 SSD。因此比较不再是一边保存新增数据、另一边不保存；同时分别记录首 token 延迟和请求完全排空的耗时。

三、正确性与长上下文能力

32K 跨路径验证：固定选择下，驻留与恢复路径的 KV、Attention、logits、token 对齐；全块选择对 Dense Attention 通过。数据恢复正确性与稀疏策略本身的近似误差分开判断。

128K 固定 GPU 工作集：每层 1024 slots，GPU KV 区合计 896 MiB；无 prefix 建缓存回放完成 3584 次 Attention 检查并对齐。GPU 不必保留完整历史，896 MiB 仅为 KV 区，不是进程总显存。

128K 缓存恢复：64K/64K、127K/1K、128K/0 定向回放通过，证明代表性恢复路径可运行，不代表完整长上下文质量验收。

32K 小样本质量：Passkey 15/15；TriviaQA 20 样本 F1 为 Dense 0.4971、Sparse 0.4923。仅为已有小样本初筛，不推广为完整基准结论。

128K 配置的 CPU KV 容量约 7.11 GiB，完整 128K prompt 的 KV 数据约 7 GiB。实验仅扩展位置缓存，没有修改模型 RoPE 频率；系统能运行与模型长上下文质量达标分别判断。

四、32K 与 128K 性能结果

平台为 V100S 32GB，Qwen2.5-7B-Instruct，权重/KV 均 FP16，单卡、batch=1。block=16 tokens，chunk=1024，四层窗口，提前一窗；Sparse 每头预算 32 blocks。

以下均为已有缓存前缀的恢复实验：32K 使用 31K 已缓存前缀 + 1K 新输入，128K 使用 127K 已缓存前缀 + 1K 新输入，输出 1 token。无请求级预热、每组一次测量，不含缓存准备。

以下耗时单位均为毫秒（ms）。TTFT 表示从提交请求到返回首个 token 的时间。每组依次列出：TTFT、首 token 后排空、含排空总耗时。

32K：

Dense SSD→GPU，写回已对齐：2183.35 / 39.09 / 2222.44 ms

Sparse CPU+GPU，预测补接前：1208.14 / 602.47 / 1810.62 ms

Sparse CPU+GPU，最新复测：1160.99 / 420.23 / 1581.22 ms

128K：

Dense SSD→GPU，写回已对齐：8548.28 / 239.82 / 8788.10 ms

Sparse CPU+GPU，预测补接前：4357.10 / 1086.32 / 5443.42 ms

Sparse CPU+GPU，最新复测：4392.98 / 1192.28 / 5585.26 ms

在 31K/1K 的缓存恢复实验中，相比 Dense SSD→GPU，Sparse CPU+GPU 的 TTFT 从 2183.35 ms 降至 1160.99 ms，降低约 46.8%；含排空总耗时从 2222.44 ms 降至 1581.22 ms，降低约 28.9%。在 127K/1K 实验中，Sparse 的 TTFT 从 8548.28 ms 降至 4392.98 ms，降低约 48.6%；含排空总耗时从 8788.10 ms 降至 5585.26 ms，降低约 36.4%。另外，在完整历史仅位于 SSD、没有新增 prompt token 的冷恢复实验中，Sparse CPU+GPU 的 32K/0 耗时为 1031.30 / 9.47 / 1040.76 ms，128K/0 耗时为 4704.64 / 39.65 / 4744.30 ms。2026 年 10 月 28 日已补齐对应 Dense 冷恢复结果及 128K Sparse 复测，见第七节；不与前面的 1K 新输入用例混算收益。以上均为单次初测，不能作为正式多次采样的最终加速比。

“排空”指首 token 返回后，剩余备份、保存和完成处理结束所需的时间，不等于纯数据传输时间。两条路径均保存新增 64 个完整 block，SSD 写入均为 56 MiB；新增数据的 1792 个 layer-block 回读匹配。

资源边界：32K Sparse GPU KV 区约 1.82 GiB、CPU 约 1.97 GiB；128K 分别约 0.875 GiB、7.11 GiB。Dense 使用 8 个循环区域，Sparse 使用 28 层独立区域，且准备状态存在差别。因此这些是有收益迹象的系统初测，尚不是同资源、正式多次采样的公平加速比。最新仅复测 Sparse，没有重测 Dense；性能运行未开启完整数值回放。

五、512K 探索：能完成，但成本过高

512K 曾因评分临时表过大无法继续。保持原有选择规则，将评分分批计算并立即归约后，完整单张临时表的形状估算由约 1.75 GiB 降至约 224 MiB；这不是整个进程峰值显存的降幅。

工作负载：无 prefix，从零处理 524288 tokens，输出 1 token。

GPU / CPU KV 容量：约 8.54 GiB / 28.11 GiB。

首 token 延迟：2255.39 秒，约 37.6 分钟。

含写回排空总耗时：2274.40 秒，约 37.9 分钟。

评分累计耗时：约 250.6 秒。

GPU slot 逐出次数：约 115.4 万次。

这次证明了容量受限下执行能走完，但未开启数值/质量验证。它与前面的缓存前缀恢复不是同一工作负载，不能直接比较耗时或计算加速比。由于总成本过高，当前已回到 128K，不继续扩大上下文。

六、当前判断与下一步

目前的主要成果是正确性闭环、固定显存工作集和 128K 系统能力；性能上，Sparse CPU+GPU 相对 Dense SSD→GPU 已出现明显的首 token 延迟优势，但收益来源仍需进一步区分。

128K 目前已经测到性能收益，但提前搬运还没发挥好：每四层要从 SSD 读取接近 1 GiB 的历史数据到 CPU，常常来不及提前备好；切换窗口时又丢掉了尚未完成的预取计划，导致选中的 KV 没有提前送入 GPU，计算时仍需等待补取。另外，有新增输入时，保存完成后还会重新整理完整历史的稀疏评分摘要，拖长请求收尾。已测的 127K/1K、128K/0 与同策略参考结果一致，未发现这些问题造成计算错误，但这不代表 Sparse 与 Dense 输出完全相同。

下一步先修好窗口切换后的预取接续，让已经安排的搬运继续完成，再用少量原配置实验检查等待是否减少。之后固定稀疏选择和 GPU 容量，对比使用与不使用 CPU 外缓存的效果，确认 CPU 缓存到底带来多少收益；暂不扩展测试规模。
