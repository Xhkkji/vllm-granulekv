## 5. 优先排查点

以下来自前一阶段代码检查，是待验证风险，不是全部已被真实运行复现的错误。下一会话先检查实际代码，按阻塞顺序处理，不把这些推测直接写成实验结论。

1. **预测状态仍可能按整个 batch 查询。** `worker.py::_restore_live_backing` 仍调用 `prediction_state(request_ids, layer_index)`；多个 correction plan 同时匹配可能报错。另一个调用点也应检查。应确认恢复和 correction 均按对应请求取状态。
2. **prefill/mixed batch 尚有缺口。** `attention/layer.py` 部分分支仍要求 `num_prefills == 1`；新增 backend 分支主要覆盖 decode。`/0` 冷恢复也可能通过 prefill 重算末尾 token，不能假设只走 decode。多 token query 的拆分必须使用真实 batch metadata，不能直接把整份 query 交给每个请求。
3. **每请求物理映射必须贯通。** `SparseKVLayerSelection` 带有 `block_table`、`slot_mapping`；检查 batch 分支是否实际使用各请求映射，尤其有界 GPU slot 的 KV 写入与 Attention 读取，不能只隔离逻辑 block 集合。
4. **LOADING 合并需匹配层范围。** `_prepare_host_read` 的生产者识别可能只看 key 和 virtual engine，未充分匹配当前四层范围。不能把不同窗口的读取错误挂到同一生产者。
5. **混合请求不能提前报完成。** `_poll_host_transfers` 中 waiter 就绪不代表本请求 GPU descriptor 已完成；检查缓存完成事件、producer 失败和 wait-only 请求，防止提前 READY 或永久等待。`wait_for_host_blocks` 也要能推动依赖的 producer 完成。
6. **abort 必须隔离。** producer 请求退出时，只要仍有 waiter 就不能把公共读取当失败取消；原生 DMA 未完成前不能释放 host slot 或 in-flight 保护。
7. **同 prefix 的调度计划复用。** 检查 scheduler 是否在第一个恢复请求后 pop 了共享 sparse plan，导致第二请求使用不同策略。

次级检查：D2H 备份仍有使用全局选集的路径；host WRITE 可能等待整个 virtual engine 的读取；XFormers 新分支的数值记录与 Torch SDPA 的实际 index 长度需要核对。这些会影响完整验证或耗时解释，不要先做无关性能重构。

主要入口：`vllm/core/async_kv_scheduler.py`；Figure13 在 `vllm/core/custom_schedulers/hierarchical_io/figure13/scheduler.py`；batch barrier 在 `vllm/worker/worker_base.py`。不要误把通用 scheduler 放到 sparse policy 中。
