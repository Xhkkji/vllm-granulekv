# 20261024 优化思路和协同方案

> 整理日期：2026-10-24。本文记录当前代码审计、已有实验事实，以及 CPU + GPU 协同的后续实施思路。
> 本文不是实现完成报告；“建议修改”均尚未据本文实施。仅新增本文，不修改原有核心逻辑文档、1008 汇报或既有验证报告。

## 1. 核心目标与结论

主线保持不变：**SSD 保存完整 KV，CPU 以较大的批量读取建立完整 backing，GPU 按稀疏选择持有和消费工作集，并通过逐层预取隐藏必要传输。**

- 当前立即需要的一批 KV 可以从 SSD 直接进入 GPU；其余 KV 批量进入 CPU，后续按需 H2D。
- CPU 的目的不是替代 SSD 后再无条件把全量 KV 搬入 GPU，而是把 SSD 的批量吞吐和 GPU 的稀疏消费解耦。
- 已在 GPU、版本有效且之后仍需要的 KV 应保留；只有真实覆盖、版本失效或请求清理才能撤销其有效驻留。
- GPU 上产生的新 dirty KV 必须有正确 backing；已存在有效副本的 clean KV 不重复备份或重写 SSD。
- 维持 32 KiB block-level `[K block | V block]`，不修改选择算法、token 数、RoPE 位置或 SSD 既有字节顺序来制造收益。

**CPU 外缓存方案在结构上可行，但当前实验尚未证明它在所有场景下具有端到端净收益，也尚未证明完整 KV 超出 GPU 容量时可运行。** 当前实现已经具备批量 SSD→CPU、稀疏 H2D、逐层独立 GPU region、owner/pending/fence 等基础；主要欠缺是完成登记与消费衔接，以及超显存所需的有界物理映射。

稀疏选择不是未经验证的性能退化解释。必须分别核对实际读集、字节数、驻留命中、控制成本、关键路径等待和重叠，再判断瓶颈。

## 2. 当前三级 KV 的真实使用方式

### 2.1 当前模型与字节口径

当前目标实验为 Qwen2.5-7B-Instruct、28 层、4 个 KV heads、head dimension=128、FP16 KV、block size=16。

```text
单层单 K 或单 V block = 16 KiB
单层完整 K+V block = 32 KiB，使用一条 paired descriptor
一个覆盖全部 28 层的逻辑 block = 28 × 32 KiB = 896 KiB
每 token 全层 KV = 2 × 28 × 4 × 128 × 2 bytes = 56 KiB
32768 tokens 的完整 KV = 1.75 GiB
```

16 KiB/32 KiB 指 descriptor 描述的数据长度，不是 descriptor 结构体自身大小。下文区分“跨全部层的逻辑 block”和“单层的 layer-block”，不混用计数。

### 2.2 实际分配与用途

| 层级 | 当前配置 | KV 数据区容量 | 当前使用方式 |
| --- | --- | --- | --- |
| GPU | 28 个独立 region，每层 2135 slots | 1.824 GiB | 直接恢复、稀疏实际选择、预测和新生成 KV 的目标空间；完整 32K KV 也能放下 |
| CPU pinned host | 28 个 region，每层 2304 slots | 1.969 GiB | SSD prefix backing 与新计算历史 backing；最终完整 32K prompt KV 约 1.75 GiB |
| SSD 逻辑槽空间 | 18724 个全层逻辑 block | 约 16 GiB | 保存完整 KV；单份 32K 为 1.75 GiB，不代表所有实验副本的总占用 |

GPU/host 实际对齐分配约为 1.827/1.970 GiB。上述数值不包含模型权重、代表向量、评分张量、Attention workspace、descriptor pool 和其他运行时内存。SSD 的 16 GiB 是当前逻辑槽配置，不是物理 SSD 的总容量。

日志中的 `# CPU blocks: 18724` 在当前 GranuleKV 路径中用于 SSD storage slots，不能当作实际 pinned-host block 数。实际 host 为每层 2304 slots。

### 2.3 “使用率”不能混为一个数字

| 指标 | 当前可确认的结果 | 不能据此推导的结论 |
| --- | --- | --- |
| 完整 KV 对预分配容量的比例 | 32K 完整 KV 占 GPU KV 区 95.93%，占 host KV 区 88.89% | 不代表 GPU 实际驻留了全部 KV |
| Attention 的 selected/full block 比 | 16K/16K 约 24.2%；32K/0 约 12.54% | 跨层、跨 chunk 的累计访问比例不是同时驻留率 |
| 32K/0 最终实际选择 | 跨 28 层共 7191 layer-block，约 224.72 MiB | 不包含全部预测驻留，不等于已分配显存 |
| `resident_coverage=100%` | 消费所需集合获得覆盖 | 不代表整个 cache 满载或显存利用率为 100% |
| 实际有效 GPU 驻留率 | 现有结果缺少逐时刻 owner 快照，不能准确报告 | 不能用累计 H2D 字节或命中次数代替 |

**当前实现已经减少访问和搬运，但 GPU 容量仍按完整上下文预留。稀疏访问不等于稀疏容量管理。** 后续应在已有统计中补充分配容量、有效驻留高水位、当次消费集合及其交集，不新建一套监控框架。

## 3. 已有证据：协同有效的部分与尚未兑现的收益

### 3.1 已实现的路径

`_enqueue_hierarchical_prefix_restore()` 当前把第一窗口的初始选择直接送 GPU，其余逻辑 block 跨全部 28 层批量送 host，并补齐首窗选择在后续层的 host 数据。后续窗口不再为这些 host-owned 数据重复发 SSD 读取。

这符合“给 SSD 足够批量，再从 CPU 稀疏传 GPU”的方向。现有正式采样未报告重复 SSD read 错误，但这不自动证明其调度和完成粒度最优。

### 3.2 现有 output=1 流量与性能

总 prompt=32768；每点 3 次预热、10 次正式采样；以下流量为每请求统计，H2D 有样本差异时取平均。

| 操作 | 16K prefix / 16K suffix | 32K prefix / 0 suffix |
| --- | ---: | ---: |
| SSD 总读取，GPU+host | 896 MiB | 1792 MiB |
| CPU→GPU | 583.06 MiB | 245.69 MiB |
| GPU→CPU | 900.50 MiB | 5.25 MiB |
| CPU→SSD | 896 MiB | 1792 MiB，存在全量重写问题 |

冷请求把完整 prefix 放入 CPU，所以 SSD 总读取量并未因为稀疏而减少。收益需通过后续复用、减少计算/GPU 数据访问和隐藏传输兑现；不能把本来就计划读取的完整 host backing 判为“绕过选择全量 H2D”。

同容量、28 层独立 region 的层级 Dense 对照中：

| 点 | 层级 Dense TTFT p50 | Sparse TTFT p50 | Sparse 相对差异 |
| --- | ---: | ---: | ---: |
| 16K/16K | 8619.34 ms | 6884.41 ms | 约降低 20.1% |
| 32K/0 | 1422.32 ms | 1673.29 ms | 约增加 17.6% |

这是整条链路的比较，不能单独归因于 CPU 缓存。Dense 对照是 GranuleKV 的层级直接恢复路径，不是原版 Tutti 的论文结果；旧 closed-gate Dense 的容量与调度也不同，不能混作同一个基线。

### 3.3 当前收益受限的具体原因

1. **Host READY 粒度过粗。** `_poll_host_transfers()` 等整笔 host request 完成后，`_mark_host_ready()` 才发布其中所有 layer-block。当前层可能被其他层的数据拖住；没有有效完成凭据时不能猜测某些数据已可消费。
2. **GPU 提前传输依赖上述 READY。** `_prefetch_next_layer()` 只提交 host READY 的预测块；缺失 READY 就不提前提交，最终 actual correction 仍可能在消费前补取。
3. **重叠比例仍小。** 独立 profiling 样本中，16K H2D 75.75 ms，与模型计算交集约 2.19 ms；32K H2D 35.07 ms，交集为 0。profiling 数字不能替代无 profiling 的正式耗时。
4. **选择和控制仍有成本。** 多 chunk 需要实际选择与映射管理，反馈重复 scoring 已消除，不应继续把它当作待消除的问题。评分、控制等待、CPU 提交和 GPU copy 计时有包含关系，不能直接相加。
5. **结束时存在 SSD 全量重写。** 这是独立的生命周期登记错误，不是稀疏算法导致。写盘排空主要影响含排空耗时，不能把全部 drain 都计成 TTFT。

CPU→GPU 的介质传输优势本身不保证端到端更快；CPU backing 建立、Selection、完成通知和提交的顺序都必须进入比较。现有冷恢复实验也不能单独量化跨请求 CPU 热缓存收益，当前实现没有引入跨请求缓存。

## 4. 先解决冗余写回：明确错误所在

### 4.1 不混淆两段写回

`_back_up_layer()` 已排除 host 有有效副本且本轮未改写的 clean block，也避免 clean block 的 pending D2H 重复提交。D2H 的主要对象是 dirty KV 和缺少 host 副本的 GPU-only KV。

16K/16K 的 900.5 MiB D2H 可由 896 MiB 新 suffix KV 加 4.5 MiB 首窗 GPU-only backing 解释。Partial tail 更新后的再备份属于新版本，不能直接记作同版本冗余。现有聚合统计不支持“大规模重复 GPU→CPU”的判断，但也不能替代逐笔版本/mapping 核验。

已确认的大额错误发生在 **CPU→SSD**：部分单 forward 结束的请求重写完整 1.75 GiB prefix。层级 Dense 也出现同类问题，只是其写源为 GPU。

### 4.2 根因与最小修复方向

当前顺序：worker 已完成消费 → output processing 触发 `free_seq()` → `_try_start_granulekv_prefix_store()` 建表 → scheduler 才处理剩余 restore 完成登记。

`_storage_replicas` 由 `commit_granulekv_prefix_restore()` / `finalize_granulekv_prefix_working_set()` 登记；`_build_storage_targets()` 提前执行时看不到干净 SSD 副本，于是生成全量 WRITE mapping。之后登记完成不会自动缩小已经排队的写回。

建议直接修改现有生命周期入口：

- 复用 engine 的 I/O event 收集和 `complete_ready_async_kv_transfers()`，使已完成的 restore 在 store mapping 建立前完成登记。
- 对尚未完成 restore 的 finished 请求，利用现有 `hierarchical_prefix_loading` 保留资源，并在既有终态处理中继续 store；不新增独立写回队列，不 busy-wait。
- `free_seq()` 与 group 清理都必须尊重这项依赖；只登记已确认完成的副本，不把 forward 结束当作 DMA 完成。
- Sparse restore 不发布“所有 KV 已驻 GPU”的全局 cache 命中；clean SSD 副本登记与 GPU 全驻留是不同语义。
- dirty/version 判断、D2H backing、error/abort 与源资源保护保留；禁止通过丢弃必要写回来减少字节。

验收：覆盖 output=1 同轮结束、output=2、多 chunk、部分 restore 尚未完成、error/abort；已有有效 SSD 副本不进入 WRITE mapping，dirty 数据 read-back 对齐，store 只启动一次，资源只释放一次。

## 5. 衔接批量 SSD 读取与稀疏 H2D

### 5.1 批量大小与完成粒度分开设计

GranuleKV executor 已有 1024-slot descriptor pool、`progress()` 回收和 `_refill_pool()` 持续补请求；后者按 READ 优先、请求开始顺序供给。当前 client/connector 对外仍是整请求完成，不提供可直接使用的 layer-block 局部 READY。

**优先复用现有窗口请求取得更细完成事件，而不是扩大 wire 协议或新增逐 descriptor 通知。** 大量并行 descriptor 可以来自一个窗口，并不要求 28 层共同等待一个完成事件。

### 5.2 具体组织方式

在 `_enqueue_hierarchical_prefix_restore()`、worker host staging 与已有 rolling runtime 上修改/复用：

1. 第一窗口仍将初始选择直接送 GPU，host 读取该窗口的补集。
2. 后续按既有 `window=4` 组织该窗口完整 prefix 的 host backing；不再另保留跨 28 层 bulk/tail 重复覆盖同一地址。
3. 复用 staged/active/pending 管理，有界地让后续窗口进入 I/O；host/GPU/read/write 必须共同遵守实际 request slot 上限，不能各自按上限提交。
4. 窗口内仍批量构造 descriptor，使用同一 pool 持续 refill；不是逐 block 小请求，也不是等一窗彻底结束才开始准备下一窗。
5. 每窗完成仅登记对应 host blocks；保留真实完成、版本与错误校验，不提前发布 READY。

32K 的完整四层窗口包含 8192 个 paired descriptors、256 MiB 数据，仍明显大于 1024-slot pool。它说明缩小完成范围不必等价于零散小 I/O，但**不能替代带宽实测**。窗口 READY 可能仍不是最优粒度，本轮先验证现有机制能否解决主要等待，不预设继续细分。

第一窗口 direct-to-GPU 的块通过现有 GPU-only backing 建立 host 副本；其余层走对应 host 窗口。应按 `(request, layer, logical block)` 核对覆盖，保证总 SSD 字节不增、无重复读取、无缺口。

### 5.3 接上已有预测与按需补取

- 保留 `_release_hierarchical_layer()` 在当前 decoder layer 的 Python 计算提交后调用 `_prefetch_next_layer()`，随后提交当前层必要 D2H。
- Host 窗口更早 READY 后，下一层已有预测中 GPU 未命中且无匹配 pending 的块，进入同一个 H2D helper。
- 预测仍用现有上一轮实际 immutable-prefix 选择；冷启动仍用原初始 plan。当前层 Query 出现后只做一次实际选择，命中或匹配 pending 复用，仅补缺失。
- 预测集合不等于本轮实际集合。不得承诺全部数据提前到位，不通过偷偷扩大选择或全量 H2D 提高命中。
- 不新增预测器、copy stream、packing buffer 或全局同步；不能为了 H2D 优先越过必要 release/backup fence。

验收同时看首个关键窗口 READY 时间、后续 refill 连续性、有效带宽、H2D 提交/完成与消费等待、真实计算交集、预测浪费和含排空耗时。若窗口化丢失吞吐或控制开销抵消收益，应据实报告，不把“请求拆开了”当作优化成功。

## 6. 扩展到超显存与约 1M 的可行性边界

### 6.1 必须做超显存实验，但不能只调长度

当前 `llm_engine` 根据 `max_model_len` 和 watermark 计算完整历史所需 GPU block 数；容量不足会报错。恢复直接使用 `table[logical_block]`，所以“完整历史候选”与“完整历史都有物理 slot”仍绑定。

| 上下文 | 完整 FP16 KV，不含权重与工作空间 |
| --- | ---: |
| 32K = 32768 | 1.75 GiB |
| 128K = 131072 | 7 GiB |
| 256K = 262144 | 14 GiB |
| 512K = 524288 | 28 GiB |
| 100 万 tokens | 约 53.41 GiB |
| 1M = 1048576 | 56 GiB |

本机 GPU 是 32 GiB V100S，现有实验权重约 14.25 GiB；512K 完整 KV 与权重已经不能同时驻留，1M 更不可能。固定较小 GPU KV 预算时，更短上下文也可验证超预算场景。32K 的价值是回归和归因，不是证明稀疏容量管理。

### 6.2 最小必要能力：逻辑 block 与物理 slot 解耦

- 保留 28 层独立归属与固定 GPU 工作集预算，不恢复 `layer % 8` 跨层覆盖，也不随上下文继续扩大 GPU cache。
- CPU/SSD 保持完整逻辑历史；GPU 只为选中、预测以及当前写入所需 block 提供有界 slot。
- 扩展现有 owner/pending 映射的职责，保留有效命中，仅为缺失数据选择可安全复用的目标；dirty、消费中、H2D/D2H 在途和版本依赖都必须保护。
- Writer 的 slot mapping、H2D/SSD destination、Attention 的 block table 必须使用同一层的映射；selector、代表向量、RoPE 与因果边界继续使用原逻辑位置。
- 这不是改一个表名即可完成。当前 block manager 的准入、逻辑历史记录及物理分配关系也需要核对；不通过绕过容量检查伪装支持。
- 先做目标路径的有界映射，不设计通用 allocator；sink/local 的物理保留与轮换策略需服从实际读集和安全覆盖，不额外堆叠 prediction keep 机制。

这项能力超出“写回顺序 + 窗口 READY”的局部修复范围，应作为独立阶段明确设计和验收；本文不宣称已有完整实现方案或已通过 1M 验证。

### 6.3 另外必须核对的资源与质量边界

| 项目 | 当前限制 | 扩展前要求 |
| --- | --- | --- |
| CPU backing | 当前仅约 1.97 GiB | 完整 1M 需至少约 56 GiB KV 数据区，再加输出和对齐余量；本机约 503.6 GiB RAM 仅说明容量有条件，pinned 分配仍需验证 |
| SSD catalog | 当前逻辑槽约 16 GiB | 验证可用 SSD 地址范围及副本空间，扩容逻辑槽，不覆盖既有有效数据 |
| Scoring 中间张量 | 多 Query 先生成 `[chunk, heads, candidates]` 再取 chunk 最大值 | 1M、chunk=1024 时，单份 FP16 scores 约 3.5 GiB；评估现有入口内分段归约，保持同样最大值与稳定 top-k，不改变稀疏算法 |
| Metadata 与控制 | 代表向量、索引、descriptor 请求列表随上下文增长 | 核对常驻量、峰值及 CPU 构建成本，不能只统计 KV 数据区 |
| 初始 SSD populate | 当前实验可在完整 GPU 容量内准备 | 超显存时需分段计算/保存，不能先要求完整 KV 驻 GPU 才能开始实验 |
| 模型位置与质量 | 本地配置 `max_position_embeddings=32768` | 扩大 RoPE buffer 不代表 1M 质量成立；明确长上下文模型/位置配置，区分 I/O 容量实验与质量验收 |

可借鉴 Tutti 的逐层读取/计算组织、SolidAttention 的物理布局与选择复用思想，但以本系统接口为准。不能把当前 GranuleKV 测试称作原论文复现，也不能直接把其他模型的稀疏结构视作当前模型已具备的能力。

## 7. 实施顺序与验收边界

| 阶段 | 主要修改 | 验收重点 |
| --- | --- | --- |
| A. 完成登记与写回 | 既有 engine/scheduler/store 生命周期 | 干净 SSD 副本复用，dirty read-back 正确，finish/abort 和资源生命周期不回退 |
| B. Host 窗口完成 | 既有窗口请求、host staging、pool refill | SSD 不重读、不漏读、不丢吞吐，关键窗口更早 READY，H2D 与计算实际交集 |
| C. 固定预算 GPU 映射 | 既有 owner/pending、block/slot mapping 及消费者 | 完整逻辑历史超出 GPU 预算仍运行，跨层不 alias，命中保留，覆盖受 fence 保护 |
| D. 长上下文准备 | Host/SSD 容量、metadata/scoring、populate 与模型配置 | 容量可控、选择语义不变、可建立超显存初始数据，质量与系统性能口径分离 |
| E. 分级扩展 | 固定 GPU 预算下 128K→256K→512K→1M | 正确性、字节流量、TTFT/首次 decode/排空、峰值内存和真实重叠逐级报告 |

每一步先验证对应语义再推进。32K 回归沿用现有 resident/固定选择 replay、all-block 对 Dense、KV fingerprint、Attention/logits/token、Passkey 和本地 TriviaQA；小样本质量不冒充完整 benchmark。

性能优先 output=1，补 output=2 首次 decode；保持相同模型、RoPE、容量、初始 residency、warmup=3 和正式采样=10。SSD 准备不计入请求计时，但准备成本另报；生成、写回排空和含排空耗时分开。Nsight 串行单独运行，不混入正式采样。

中间阶段性能波动记录归因，不因此自动放弃尚未完成的计划内工作；正确性/地址覆盖失败先定位，不能用全量恢复、丢 dirty、加大全局 cache 或同步兜底。需要计划外复杂机制时停下解释。超过容量的 Dense 应明确标为不可运行，或使用清楚定义的 out-of-core 对照，不能偷偷扩大其显存预算。
