# 2026-11-09 KVCache 工作汇报

## 一、本阶段目标

本阶段围绕多请求 Sparse 链路，重点解决相同历史 block 在多个请求之间重复读取的问题，并验证真实 batch=2 的正确性和性能。

## 二、完成的工作

1. 为不可变历史 block 建立统一身份，将 prefix、逻辑 block 和层作为共享判断依据。相同 prefix 的历史数据可以跨请求复用；`/0` 末尾重算位置、suffix 和新增 KV 仍保持请求独立，避免把可变数据错误共享。
2. GPU 读取路径增加了 READY 和 LOADING 两种复用处理。已有 GPU 副本直接使用原物理 slot；已有传输尚未完成时，后续请求挂接到同一个 producer 并等待完成，不再为同一 block 再提交一笔 SSD→GPU 读取。共享 slot 的引用、owner 和释放 fence 会等所有消费者完成后再清理。
3. CPU 和 SSD 路径使用同一套 block 身份衔接。CPU 已有 READY 副本时，GPU 恢复直接走 H2D；GPU 数据正在读取而 CPU 尚无副本时，CPU 请求等待已有 GPU 传输完成，再通过原有 GPU→CPU backing 生成副本，不额外从 SSD 读取；GPU 和 CPU 都没有副本时才发起首次 SSD 读取。
4. 请求退出时只释放自己的引用，仍被其他请求使用的副本和 DMA 不会被提前取消。补充了共享读取、LOADING 等待、GPU→CPU backing、失败传播、延迟完成、请求退出和旧完成通知等单元测试，并将 SSD 读取统计改为按共享 block 身份去重。

整体数据流仍保持原来的四层 mixed 方式：每个请求在每个窗口内先得到自己的预测选集，预测并集直接准备到 GPU，补集进入 CPU；实际计算发现预测不足时，再从 CPU 或 SSD 补齐。共享只发生在不可变历史 block 的副本和传输层面，不合并两个请求的选集、查询边界或新增 KV。每个请求仍保留自己的逻辑到物理映射，因此同一个历史 block 可以被多个请求引用，而不同请求的新增数据不会互相覆盖。

传输完成后，GPU READY 副本可以直接参与 Attention，CPU READY 副本可以作为后续 H2D 的来源；LOADING 状态只登记等待关系，不重复创建读取任务。只有传输完成、消费者引用释放且物理 slot 的使用 fence 已满足时，副本和 slot 才会被清理。这保证了请求结束顺序不同、GPU 和 CPU 完成顺序不同的情况下，仍不会提前释放正在使用的数据。

## 三、正确性结果

在 Qwen2.5-7B、FP16、V100、1K、输出 2 token 的配置下，完成了真实 batch=2 验证。测试记录了同一次 model forward 中的 request ID，确认不是两个请求顺序执行后再合并统计：

| 场景 | 实际最大 batch | 结果 |
| --- | ---: | --- |
| 相同 prefix，`/0` | 2 | 通过 |
| 不同 prefix，`/0` | 2 | 通过 |

两组测试均使用独立的 batch reference 进行对照，分别检查了请求边界、每请求选集、物理映射、历史 KV、Attention 输出、logits 和生成 token。结果全部通过，误差容限保持 `rtol=atol=0.02`。

相同 prefix 场景中，两个请求能够共享 immutable 历史 block，重复 SSD 读取统计为 0；不同 prefix 场景中，两个请求不会误命中对方的 block，读取量保持各自独立。相关 Worker、scheduler、Sparse Attention 和验证检查器测试已通过，静态语法检查也通过。

验证还覆盖了传输尚未完成时的第二请求等待、GPU 数据转存 CPU 时的单次 backing、请求提前退出、异步完成通知重复到达以及共享 block 失败传播等情况。测试中的 batch 选取和物理映射均按请求分别核对，避免只验证最终输出而遗漏请求之间的映射串扰。

本次正确性结果覆盖 1K 的 `/0` 场景，证明当前 batch 组织、共享读取和生命周期处理在该场景下正确；尚未扩展到 32K/128K 长上下文，也不代表性能已经验收。

## 四、batch=2 性能结果

配置为 Qwen2.5-7B-Instruct、FP16、单卡 V100、block=16、四层窗口、每头预算 32、输出 2 token。每种缓存状态各采样 3 次。总耗时包含首 token 后排空和必要的写回处理。

加速比定义为：两个请求顺序执行总耗时 ÷ batch=2 总耗时。

| 缓存状态 | 两请求顺序执行平均总耗时 | batch=2 平均总耗时 | 加速比 |
| --- | ---: | ---: | ---: |
| 冷 CPU | 3590.7 ms | 4622.2 ms | 0.777x |
| 热 CPU | 3608.7 ms | 4456.0 ms | 0.810x |

当前 batch=2 仍然比顺序执行慢，没有取得端到端收益。相同 prefix 场景下，顺序执行的 GPU 直读 block 合计约 504 个，batch=2 约 259 个；SSD 读取从约 91.7 MB 降至约 59.6 MB。但 CPU→GPU 搬运量基本没有减少，同时 batch 计算、同步和调度开销增加，抵消了 SSD 读取节省。

## 五、当前结论

多请求 Sparse 的基本正确性和同 block 跨层级复用已经得到验证，当前主要问题不在数据复用正确性，而在批处理后的整体执行开销。性能优化暂时暂停，不继续扩大测试范围；后续如恢复优化，应优先分析 CPU→GPU 搬运和 batch 调度开销，再决定是否继续修改实现。

## 六、后续扩展方向

下一阶段可将场景扩展到单机多 GPU，并先使用单个共享 SSD 作为功能基线。每张 GPU 保留独立的物理 slot、owner 和 fence，CPU/SSD 侧共享不可变 block 的身份和传输状态。这样可以先验证跨 GPU 的同 block 复用、LOADING 等待和请求生命周期；单盘带宽有限，主要用于正确性和调度对照，不预设性能收益。

通过单盘多 GPU 验证后，再扩展到多 SSD，为不同 GPU 和磁盘建立独立 I/O 队列，观察 SSD 带宽扩展、跨 GPU 复用和 CPU→GPU 搬运开销。Tensor Parallel 和 Pipeline Parallel 暂后处理，避免一开始引入 KV 分片和跨层映射变化。

可采用的通用 baseline 包括：当前单卡单盘 GranuleKV 作为控制组，LMCache SSD/DRAM 作为分层缓存基线，Mooncake 或 SGLang HiCache 作为共享 KV 存储基线，vLLM Tensor Parallel 作为多 GPU 计算基线。TUTTI 是最接近本项目的多 GPU、多 SSD 参考，其设计采用每 GPU 独立 NVMe 队列；但其硬件和 I/O 配置与当前 V100 环境不同，结果需要重新测量。
