# 多卡多盘扩展思路

## 一、当前结论和扩展目标

当前单卡 Sparse mixed 链路已经完成同 block 复用验证：相同 prefix 的 immutable 历史 block 可以在请求之间共享，GPU、CPU 和 SSD 读取状态可以统一处理，重复 SSD 读取已经被消除。但当前 batch=2 的端到端性能仍未取得收益，主要开销转移到了 CPU→GPU 搬运、batch 计算和同步。

因此，后续扩展的目标不是简单增加 GPU 数量，而是验证以下问题：

1. 多张 GPU 是否可以共享同一个逻辑 block 和 SSD producer，同时保持每张 GPU 的物理副本独立。
2. GPU-initiated 直通存储在多 GPU 下是否需要每 GPU 独立的提交/完成队列，才能避免队列竞争。
3. 单 SSD 的共享带宽是否会掩盖多 GPU 的收益，以及增加 SSD 后是否能够真正提升总 I/O 带宽。
4. Sparse 预测读取、实际 miss 补取和 GPU/CPU/SSD 生命周期能否在多个 GPU 上保持一致。

建议采用两阶段目标：

```text
第一阶段：单机双 GPU、单 SSD
        验证跨 GPU 的 block 共享、producer/waiter 和生命周期

第二阶段：单机双 GPU、多 SSD
        验证 per-GPU I/O 队列、SSD 带宽扩展和跨设备传输
```

单机多 GPU、单 SSD 是可行的功能基线，但不应预先假设它有性能收益。两个 GPU 共享一块 SSD 时，SSD 带宽和队列可能成为共同瓶颈；GPU 之间通过 PCIe 复制数据也可能比从 SSD 重读更慢。多 SSD 才是后续观察存储扩展能力的主要性能场景。

## 二、GPU-initiated 存储相关成果

### 1. BaM：GPU 发起细粒度存储访问

[BaM，ASPLOS 2023](https://doi.org/10.1145/3575693.3575748) 是 GPU-initiated 存储的基础工作。它的核心做法是让 GPU 线程直接产生细粒度存储请求，通过 GPU 可见的高吞吐队列访问 NVMe，并使用软件 cache 合并请求、减少 I/O 放大。

对本项目的启发是：GPU 适合直接表达“当前 query 需要哪些 block”，但逻辑选集不应直接等同于物理 I/O。仍需要在数据面前进行 block 合并、物理映射和目标位置确认。

### 2. CAM：GPU 数据面与 CPU 控制面分离

[CAM，ICDE 2025](https://doi.org/10.1109/ICDE65448.2025.00175) 研究了 GPU-initiated SSD 管理中的一个问题：如果 GPU 同时负责全部 SSD 控制，队列维护和控制逻辑会占用 SM，并可能让 I/O 与计算串行化。CAM 让 GPU 负责数据访问，CPU 负责 SSD 控制，并通过异步接口重叠 I/O 和计算。

这与当前项目的方向一致。GPU-initiated 不意味着必须把整个调度器、completion 和生命周期控制搬到 GPU。更合理的分工是：

```text
GPU：表达数据需求、发起或消费数据、执行 Attention
CPU：维护 block 元数据、producer/waiter、队列和生命周期
SSD：执行批量异步读写
```

### 3. TUTTI：GPU-centric KV 存储和多 GPU 队列

[Tutti，2026 最新预印本](https://arxiv.org/abs/2605.03375) 是当前最接近 SSD-backed KV 场景的工作。它使用 GPU-centric KV object store、GPU 侧 I/O 路径和层级读取调度，并评估了多 GPU、多 SSD 环境。

其多 GPU 设计不是让多个 GPU 共享同一个物理 slot，而是：

- 每个 GPU 进程独立管理自己负责的 KV block；
- 每个 GPU 使用独立的 NVMe submission/completion queue；
- 本地 daemon 负责建立 GPU 和 NVMe queue 的关系；
- 不同 GPU 的物理副本、队列和完成状态分别维护。

论文环境为两张 H100、四块 NVMe SSD，两个 GPU 通过 NVLink 互联，每张 GPU 对应独立的 SSD 资源。它报告了 2 GPU + 4 SSD 的多 GPU 结果，但没有直接证明跨 GPU 的同一 immutable block 只读取一次 SSD。因此，TUTTI 更适合作为 GPU I/O 数据面和多 GPU 队列的 baseline，而当前项目的 canonical block、producer/waiter 和跨请求去重仍然是需要保留的部分。

### 4. GNStor 和 SwarmIO：GPU 直连远端存储与测试方法

[GNStor](https://arxiv.org/abs/2606.04908) 将 GPU-initiated I/O 扩展到远端 All-Flash Array，通过 GPU-native NVMe-over-RDMA 访问远端 SSD。它说明 GPU 直通存储不仅可以用于本地 NVMe，也可以扩展到远端共享存储，但这会引入 RDMA、远端元数据和故障恢复问题。

[SwarmIO](https://arxiv.org/abs/2604.06668) 则提供 GPU-centric storage 的高 IOPS 仿真方法，用于评估 GPU 发起大量随机 I/O 时的 SSD 行为。它更适合作为多盘扩展时的测试和建模参考，而不是直接的 KV serving 实现。

## 三、KV cache 和 Sparse serving 相关成果

### 1. Mooncake、HiCache 和共享 KV 存储

[Mooncake，FAST 2025](https://www.usenix.org/conference/fast25/presentation/qin) 将 KV cache 作为独立的共享存储资源，支持跨实例、跨 GPU 和远端节点传输。它的重点是共享 KV pool、传输引擎、内存/SSD 分层和请求级生命周期。

SGLang HiCache 采用 GPU、CPU、分布式存储三层结构，并支持 Mooncake、3FS、NIXL 等存储后端。其设计强调：GPU 层通常是实例私有的，真正跨实例共享的是更高层的存储；TP 场景需要跨 rank 同步状态。

这些设计与当前项目的 canonical identity 方向一致，但它们通常面向 dense prefix reuse 或通用分层缓存，不能直接替代当前四层 Sparse mixed 链路。

### 2. Janus、PulseInfer、HiSparse 和 OasisKV

[Janus](https://arxiv.org/abs/2609.36938) 面向 SSD-backed Sparse KV storage，使用模型较早阶段的中间结果预测后续要读取的 KV，并将预测读取与计算重叠；预测 miss 在真正 Attention 前补齐，同时合并相邻读取并限制后台写入。

[PulseInfer](https://arxiv.org/abs/2609.34555) 重点处理 Sparse KV offloading 中碎片化的 CPU→GPU 传输，通过可中断的 layer-wise 调度、自适应 I/O 准入和 gather-scatter 合并减少传输开销。

[HiSparse](https://arxiv.org/abs/2608.07009) 将完整历史放在 host memory，只在 GPU 保留固定大小的 Sparse 工作集，并使用 layer-wise prefetch 隐藏 miss 延迟。它已经合入 SGLang，适合作为 Sparse 分层驻留的工程参考。

[OasisKV](https://arxiv.org/abs/2608.08097) 使用 lookahead sparse prefetch，在有限 HBM 中只保留即将使用的 KV，并扩展到多 GPU serving。它说明预测窗口的价值不仅在减少数据量，也在于提前确定数据进入哪一级存储。

这些工作与当前四层 mixed 的共同点是：

```text
预测选集 → 提前准备
实际选集 → 命中则复用，缺失则补取
GPU 工作集 → 有界且按层推进
```

区别在于，当前项目额外要求预测并集直达 GPU、补集进入 CPU，并保持现有评分算法和窗口边界不变。

### 3. FlatCake、Range 和多层存储管理

[FlatCake](https://arxiv.org/abs/2610.38355) 认为 DRAM 和 SSD 不应简单作为传统的上下级缓存，而应作为两个可直接放置 immutable block 的介质。它使用 session-contiguous、layer-major 的布局，并将 SSD 读取直接流入有限 GPU 工作集。

[Range](https://arxiv.org/abs/2610.21241) 进一步指出，SSD 恢复的成本不只来自字节数，还来自每个逻辑 object 的 lookup、ownership、descriptor、completion 和 release。它用物理 range 和 lease 减少逐 object 的管理开销。

这两类工作对当前 batch=2 变慢的问题非常有帮助：即使同 block 复用已经降低了 SSD 字节数，如果每个 block 仍然独立创建大量元数据和完成处理，整体请求仍然可能变慢。未来可以在不改变 Sparse selection 的前提下，增加物理范围合并和批量 completion。

## 四、这些工作的共同架构思路

### 1. GPU 数据面、CPU 控制面

GPU 适合处理高并发、细粒度的数据访问；CPU 适合维护哈希、队列、引用、失败和释放条件。当前系统应继续保持这种分工，不因为 GPU-initiated 存储而引入完整的 GPU persistent scheduler。

### 2. 每 GPU 独立物理状态

多 GPU 下，一个逻辑 block 可以对应多个 GPU 物理副本：

```text
一个 immutable logical block
    ├── SSD canonical 副本
    ├── CPU backing 副本
    ├── GPU 0 物理副本
    └── GPU 1 物理副本
```

共享的是 logical identity、producer 和存储来源；GPU slot、owner、generation、fence 和引用必须按 GPU 独立维护。

### 3. 每 GPU、每 SSD 独立队列

多 GPU 不应让所有请求共用一个全局 SSD 队列。更合理的组织是：

```text
GPU 0 ── SSD 0 / SSD 1
GPU 1 ── SSD 2 / SSD 3
```

如果物理拓扑允许，可以优先使用本地 Root Complex 下的 SSD；跨 GPU 或跨 Root Complex 的传输单独统计。单 SSD 阶段可以共用一块盘，但仍应验证多队列是否产生争用。

### 4. 逻辑选集和物理 I/O 批次分离

Sparse 评分产生的是逻辑 block 集合，不代表每个 block 必须独立提交一次 I/O。物理层可以合并相邻 block、同层 block 或同一窗口内的多个请求，减少 descriptor、队列和 completion 开销，同时保持逻辑选集不变。

### 5. 预测、准入和实际使用分离

预测命中只说明未来可能使用某个 block，不代表当前必须马上占用 GPU slot。可以根据：

```text
预计使用时间
存储读取时间
H2D 时间
当前 GPU 工作集容量
```

决定何时真正提交读取和保护 slot。当前只需保持现有窗口策略，后续再考虑更细粒度的 timing-aware admission。

### 6. 读写队列隔离

新增 KV 写回、SSD→GPU 恢复和 SSD→CPU backing 同时发生时，后台写入不能无限制抢占恢复读取。Janus、SARIA 和 FlatCake 都强调读取优先、写回限速或读写队列隔离。多 GPU 后尤其需要按读/写、GPU/SSD 和请求分别记录队列等待时间。

### 7. 共享 block 的一致性和生命周期

共享 block 需要明确：

- canonical identity；
- 唯一 producer；
- LOADING waiter；
- consumer lease/refcount；
- generation/version；
- GPU slot release fence；
- producer 或 consumer 提前退出后的处理。

HotStorage 2026 的一致性分析表明，分布式 KV cache 中 reader lifetime、slot reuse、retirement 和“缺失状态”不能简单依赖一个中心状态，需要明确哪些状态可以单调发布，哪些状态必须等待协调。

## 五、对本项目的具体设计建议

### 阶段一：单机双 GPU、单 SSD

建议先采用 Data Parallel，每张 GPU 处理不同请求，避免立即引入 Tensor Parallel 的 KV head 分片。

初始结构为：

```text
GPU 0：请求 A，独立 GPU resident map
GPU 1：请求 B，独立 GPU resident map
             │
             ▼
共享 CPU/SSD canonical directory
```

需要分别测试三种同 block 获取方式：

1. GPU 0 和 GPU 1 都从 SSD 独立读取；
2. GPU 0 作为 producer，GPU 1 通过 GPU P2P 获取；
3. GPU 0 读取完成后生成 CPU backing，GPU 1 通过 H2D 获取。

这三种方式应作为明确实验组，不应在运行时根据不稳定条件任意切换。V100S PCIe 环境必须先确认 `nvidia-smi topo -m`，不能直接套用 TUTTI 的 H100/NVLink 结果。

单盘阶段重点验证：

- 同一个 immutable block 是否只有一个 producer；
- 第二个 GPU 是否能正确挂接 LOADING 状态；
- 两个 GPU 是否各自建立正确的物理 slot 和 fence；
- producer 或 consumer 提前退出是否影响另一方；
- 不同 prefix 是否始终隔离；
- GPU P2P、CPU 中转和 SSD 重读的实际耗时差异。

### 阶段二：单机双 GPU、多 SSD

通过单盘正确性后，再引入多 SSD。建议初始使用确定性 hash 或 prefix 范围进行 block 放置：

```text
canonical block identity
        ↓
确定性选择目标 SSD
        ↓
每盘独立提交队列
        ↓
同一 block 的唯一 in-flight producer
```

第一版不建议立即引入动态迁移、热 block 复制或复杂 allocator。先比较：

- 单 SSD 单队列；
- 单 SSD 多队列；
- 多 SSD 独立队列；
- 多 SSD RAID0 作为聚合带宽参考。

RAID0 可以作为上限参考，但不适合作为唯一实现，因为它隐藏了 block 到具体磁盘的映射，不利于统计 per-disk load、同 block 去重和队列等待。实际系统更适合保留 canonical block 到目标 SSD 的显式映射。

### 阶段三：物理范围合并和跨设备传输

在多盘路径稳定后，再考虑两类优化：

1. 将逻辑上相邻或同窗口的 block 合并为物理 range，减少 descriptor 和 completion；
2. 根据拓扑比较 SSD 重读、GPU P2P 和 CPU 中转，选择最短的数据路径。

这些优化不应改变评分算法、预测选集、四层窗口边界或 Attention kernel，只改变物理传输组织。

### 阶段四：Tensor Parallel 和 Pipeline Parallel

Tensor Parallel 暂后处理。TP 下同一个逻辑 block 可能按 KV head 或 rank 分片，canonical identity 至少需要扩展为：

```text
prefix + logical_block + layer + tensor_parallel_rank
```

不同 rank 的内容不一定相同，不能直接复用当前单卡的 `prefix + logical_block + layer` 身份。

Pipeline Parallel 还需要把 stage 和 layer range 纳入副本所有权管理，并处理 stage 间传输，因此应放在 Data Parallel 和多盘数据面验证之后。

## 六、Baseline 和评价指标

建议保留以下 baseline：

| baseline | 用途 |
| --- | --- |
| 当前单卡单盘 GranuleKV | 控制组，验证单卡 Sparse mixed 基线 |
| LMCache SSD/DRAM | 通用分层缓存基线 |
| Mooncake Store | 共享 KV pool、跨实例复用和 SSD/CPU offload 基线 |
| SGLang HiCache | GPU/CPU/远端存储三层缓存参考 |
| vLLM 多 GPU计算 | 多 GPU 计算和通信控制组 |
| TUTTI 结构 | GPU-centric KV、per-GPU NVMe queue、多 GPU多盘参考 |

每组实验至少记录：

- 每个 GPU 的 TTFT、首 token 后排空和完整 makespan；
- SSD→GPU、SSD→CPU、GPU→CPU、CPU→GPU 的字节数和次数；
- 每张 SSD 的吞吐、队列深度和尾延迟；
- GPU P2P/NVLink/PCIe 传输字节数；
- canonical block 命中、LOADING waiter、producer 数量；
- 重复 SSD 读取、slot eviction、fence 等待和失败传播；
- GPU 计算、同步、队列提交和 completion 处理时间。

评价时需要把“读取字节减少”和“端到端耗时降低”分开报告。Tutti 的 H100、NVLink、四 SSD 结果不能直接作为 V100 的性能目标；当前 V100 环境应重新测量 GPU 拓扑、SSD 带宽和 P2P 能力。

## 七、对当前实现的边界

第一阶段只扩展数据面和共享状态组织，保持以下约束：

- 保持四层 mixed 链路；
- 保持预测并集直达 GPU、补集进入 CPU；
- 保持现有 Sparse 评分和实际 correction；
- 不修改 Attention kernel；
- 不立即引入 Tensor Parallel、Pipeline Parallel 或跨节点 RDMA；
- 不把完整 scheduler 搬到 GPU；
- 不新增独立 allocator、融合 kernel 或运行时 fallback 框架。

最终希望验证的不是“多 GPU 一定更快”，而是：在 GPU-initiated 存储条件下，多 GPU 是否可以共享 immutable block 的逻辑来源，同时保持每 GPU 物理副本独立，并通过多盘队列和物理 I/O 合并把存储带宽真正转化为端到端收益。
