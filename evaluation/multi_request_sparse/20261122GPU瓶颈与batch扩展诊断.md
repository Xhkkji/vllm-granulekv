# 20261122 GPU 瓶颈与 batch 扩展诊断

## 一、结论

**当前采样的持续 decode 主要受 CPU 管理与 GPU 工作提交限制，不能概括为 GPU 算力或显存带宽持续饱和。** batch 从1增至2，正式样本吞吐只增加约5%；batch=4在短输出检查中实际被拆成两组batch=2，原因是接纳层的保守容量预留。

本轮没有修改生产逻辑、降低选块预算、扩大GPU/CPU容量、改变调度策略或提交推送。只在仓库外适配测试入口、增加诊断包装，并新增本记录。原有暂存改动保留，前后7792个生产源码文件SHA256一致。

batch=2吞吐增加5.04%，但每请求延迟明显增长。这里总输出量随batch增加；不能直接拿145秒与277秒判断吞吐变慢。`2 × batch1服务时间 ÷ batch2服务时间 = 1.050×`是归一化工作量比，不是本轮实测的一对连续顺序请求加速比。样本各一次，不宣称稳定的5%收益。

## 三、为什么 batch=4 没有真正运行

四个请求各生成两token的检查中，实际forward为：

`[A,B] → [A,B] → [C,D] → [C,D]`

没有任何四请求forward，因此测试在“实际达到目标batch”的检查处停止，未进入512-token预热或正式采样。日志未记录传输错误、GPU slot容量异常或局部FP32失败，但不能写成batch=4独立门禁通过：同批完整参考尚未运行。

定位到的现有接纳计算如下：

1. `SolidAttentionPolicy.working_set_bound`按28个query head、每头32块、首部/局部各2块，以及2048-token chunk的129块预留，得到 **1029**。
2. `AsyncKVScheduler._start_waiting_prefix_restores`加上测试初始预测的36块，每请求GPU预留为 **1065**。
3. `SelfAttnBlockSpaceManager._can_allocate_bounded`将各请求预留相加：两请求为2130，第三请求需要3195，超过GPU容量2135，因此返回`LATER`。共享数据没有在此接纳账本中按身份去重。
4. 512-token场景还有CPU约束：每请求按完整输入和输出上限预留2080块，四请求为8320，超过8200。两token检查每请求2049块、四请求8196，没有触发这一CPU边界。

已用当前生产类的`_can_allocate_bounded`做CPU侧算术重放，确认前两请求`OK`，第三/第四请求`LATER`。该重放采用实验配置重建参数，不冒充原失败运行中逐次采集的接纳状态。

这不是Attention算子不支持batch=4，也不是已经证明实际物理数据放不下。后述batch=2时间线中，同层必需物理块为168–413个，已占用槽位为381–1088个；但这也不能保证四请求未来选集的并集始终放得下。当前预留保护最坏情况，不能直接删除安全边界或简单除以请求数。

因此，本轮不继续batch=8、不同问题组或128K扩展，不绕过规则强行凑batch，也没有静默扩大容量。

## 四、Nsight Systems：GPU是否被持续喂满

单独运行32K热态batch=2诊断，每请求96输出，在第65–80次forward采集CUDA/NVTX。前后同步只用于诊断边界；正式512-token样本没有这些包装。预热长度也为96，与正式样本不同，时间线不作为性能对照。

| 配置：相同模型、硬件、选块预算及容量；32K热态batch=2；96输出中的第65–80步；Nsight Systems 2023.2.3；只统计被跟踪推理进程的CUDA context | 测量值 |
| --- | ---: |
| 采集窗口 | 7.524秒 |
| GPU kernel执行区间并集 | 0.584秒 |
| GPU复制区间并集 | 0.022秒 |
| kernel＋复制＋清零执行区间并集 | 0.606秒，占8.06% |
| 窗口内无上述推理CUDA活动的时间 | 6.918秒，占91.94% |
| PagedAttention调用 | 448次＝16步×28层 |
| Attention V2主kernel＋reduce累计 | 约31.6毫秒 |

这里按时间区间取并集，避免把重叠工作相加。**8.06%不是SM利用率、显存带宽利用率，也不是整个GPU的忙碌比例**；外部GranuleKV/MPS服务上下文未包含在这份推理进程时间线中。结论是被测推理进程的GPU工作之间有大量空档，而不是用`nvidia-smi`判断整卡空闲。

CPU NVTX区间与空档的对应关系：

| 入口（时间包含子调用，不可相加） | CPU区间累计 | 区间内与已跟踪GPU活动重合 |
| --- | ---: | ---: |
| 同层准备 | 2.742秒 | 0.196秒 |
| 备份处理 | 2.651秒 | 0.221秒 |
| H2D source引用完成轮询 | 1.022秒 | 0秒 |
| 实际选块 | 0.931秒 | 0.191秒 |

大量空档位于现有CPU准备、备份和完成记录扫描中。GPU上确实执行了矩阵乘、选块排序和Attention，但它们没有连续占满整个窗口。当前首先应减少CPU重复管理和提交间隙；不能仅因为decode通常访存密集，就把本实现的端到端问题归因于显存带宽。

## 五、硬件计数采集未成功

另尝试用Nsight Compute 2023.2.2对真实模型的一次CUTLASS线性层kernel采集计算、DRAM和L2吞吐指标，未取得有效结果：

- 首次过滤没有采到kernel，保留`kernel_b2/`及日志。
- 调整为完整kernel名称匹配后，在replay阶段报驱动警告、设备内存备份及执行停滞。终止该profiler，保留`kernel_demangled_b2/`现场；没有再试其他replay方式，也没有修改生产路径。
- profiler退出日志确认恢复GPU时钟成功；本次模型及native daemon进程已退出，GPU恢复空闲。之前的正式样本和Nsight Systems报告不受此次诊断失败影响。

因此，本轮可以判断当前采样的端到端链路主要受CPU管理与提交限制，**仍不能严谨区分每个GPU kernel内部究竟受计算吞吐、HBM/L2带宽还是并行度限制**。也不将profiler停滞记为正常生产运行的死锁。

## 六、正确性与下一步

- batch=1两token门禁：56次映射、逻辑KV和局部FP32检查；56层步、2次logits及输出token对照通过。
- batch=2两token门禁：112次映射、逻辑KV和局部FP32检查；每请求56层步、2次logits及输出token对照通过，原容差不变。
- 两组正式样本均完成所有512输出和排空，无source引用残留检查失败。没有将512步全部做独立数值验证。
- batch=4的224次局部检查未记录数值错误，但因未真正成批而停止；其summary整体为失败，不纳入性能表。

建议下一步仍先在现有batch=2收敛`_back_up_layer`分类和`_poll_host_cache_uses`扫描。扩大batch需要单独审查接纳层的共享容量计费，以及未来私有增长/选集分化的安全预留；不能只将`max_num_seqs`改大，就声称已经支持更大的有效batch。
