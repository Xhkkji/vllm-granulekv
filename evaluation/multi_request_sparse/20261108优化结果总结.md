## 改动与正确性

Worker 的 GPU logical-to-physical mapping 和 resident 均改为按请求、层分组。槽位预留另维护 `(virtual_engine, layer)` 占用集合；普通分配不再扫描全部请求，淘汰只访问当前请求与层。mixed 窗口继续从各层占用并集中选择共同槽位，物理 owner、DMA、引用及 fence 生命周期未改变。

XFormers Sparse request 的区间、长度、prefill/decode 属性和相对起止张量在 metadata builder 中每次 forward 准备一次。Attention 各层复用这些稳定字段，每层物理表、slot mapping 和选集仍独立读取。

三组真实 GPU/SSD 检查全部通过：同 prefix `/0`、不同 prefix `/0`、同 prefix suffix32。每组记录到同次真实 forward batch=2；每个请求覆盖 28 层 × 2 步及两次 logits。独立参考比较、历史 KV 指纹和局部 FP32 Attention 检查均通过；选集一致，KV、Attention 和 logits 最大绝对误差为 0，生成 token 一致，容差保持 `rtol=atol=0.02`。

回归结果：Worker、Sparse Attention 和验证检查器 `118 passed`；GranuleKV mixed/protocol `18 passed`；语法编译和 `git diff --check` 通过。相关 block/scheduler/hierarchical suite 合并运行时有两个 `test_host_prefix_write_excludes_partial_and_uncomputed_blocks` 参数用例失败，但 `test_async_kv_scheduler.py` 单独运行 `42 passed`，两个失败参数单独运行也通过。这是测试合并运行的顺序/环境差异；本次修改未触及 scheduler，未将组合失败计作通过。

## 正式端到端性能

Qwen2.5-7B FP16、V100S、eager XFormers、block=16、window=4、lead=1、每头预算32、输出2 token。每种场景与 cache 状态各 3 次；对比同两请求顺序执行服务时间之和与真实 batch=2 总服务时间。计时包括输出、写回和传输排空。CPU cache 容量按场景配置：`/0` 为 264 slots（231 MiB），suffix32 为 272 slots（238 MiB）。表中为中位数。

| 请求场景 | Cache | 顺序（ms） | Batch=2（ms） | 加速比 |
| --- | --- | ---: | ---: | ---: |
| 不同 prefix `/0` | 冷 | 477.3 | 451.6 | 1.057x |
| 不同 prefix `/0` | 热 | 474.6 | 446.2 | 1.063x |
| 同 prefix `/0` | 冷 | 464.0 | 471.4 | 0.984x |
| 同 prefix `/0` | 热 | 454.9 | 417.7 | 1.089x |
| 同 prefix suffix32 | 冷 | 582.0 | 534.4 | 1.089x |
| 同 prefix suffix32 | 热 | 585.1 | 541.8 | 1.080x |

不同 prefix `/0` 的中位改善约 6%；同 prefix `/0` 冷态略慢、热态改善约 9%。suffix32 冷/热中位改善约 9%/8%，但热 batch 样本为 1169.0、537.2、541.8 ms，波动明显，不能据此宣称稳定收益，也不外推长上下文或持续 decode。所有 batch 性能样本都通过真实 batch=2 和 token 一致性检查。

不同 prefix 冷 batch 每组读取14个 SSD 请求、112 MiB；热样本读取14个请求、63 MiB。热 batch 样本记录 392 次 host cache hit、约48.4 MiB H2D 复制、无 CPU cache loading wait、无 GPU 容量拒绝或传输错误。逐请求 TTFT、结束时间、吞吐和每样本 I/O/stat counters 保存在 `optimized_performance_*_final/summary.json`。
