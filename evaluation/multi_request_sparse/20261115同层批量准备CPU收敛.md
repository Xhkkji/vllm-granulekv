# 同层批量准备 CPU 开销收敛（2026-11-15）

本轮仅修改现有 Worker 的身份计算、绑定调用和恢复收尾，保留此前未提交的正确性修复。未 commit、未 push。三项局部修改和相关回归已完成，但整体性能验收未通过：32K 长输出 batch 已回到旧可运行版水平，冷态顺序服务复核后仍比旧版慢约 8%。按停止条件暂停后续 1K/128K 真实门禁与性能扩展，没有叠加其他优化。

## 实现

1. `_correct_bounded_batch` 为本层各请求生成一次逻辑块到 canonical identity 的局部字典；容量检查、已有副本查询、destinations 和新目标登记复用它。预留函数接收整批必需集合；其他调用沿用原入口，只有容量不足时才构造回收所需身份集合和候选。
2. 已有有效映射、消费者引用和 READY resident 状态直接复用；新消费者、目标变化、READY 推进或缺少 H2D 消费记录时仍调用原绑定入口。只有缺失身份进入预留，私有尾块仍独立。
3. 恢复先消费已有 H2D 依赖，再按原检查得到 GPU 命中。已就绪项退出后续工作；收尾只访问本次 missing 列表，重新查询当前共享条目，仅补新消费者并消费完成依赖。没有删除 owner、旧 event/generation、source 引用和 fence 检查。

## 回归和真实门禁

- Worker、residency、runtime、scheduler、Attention、验证检查器及封存组合回归：**375 passed**。GranuleKV mixed/protocol：**10 passed**。
- 新增 5 个用例：64/8192 历史块、AB/BA 顺序的全 READY 准备；全 READY 恢复仍消费原 H2D 依赖且不重复绑定、不复制。准备阶段 canonical 转换分别为 130/16386 次（包含两个私有写入块），不调用预留；核对有序紧凑读取表、私有写入位置和物理占用。
- 现有容量 3／需求并集 3、批次外消费者、延迟 DMA、旧 generation、source 释放、私有身份和退出顺序用例随组合回归通过。
- V100 backend probe：**24组通过**，覆盖独立 FP32、AB/BA/A、长度边界及封存生命周期；每次一次写 KV、一次 Attention。
- 当前代码的 32K 同 prefix `/0` 冷、热独立门禁通过，每场景 112 个选集／逻辑 KV／局部 FP32 检查，每请求 56 层步和两次 logits；原 `rtol=atol=0.02`、immutable KV 精确比较、token 一致性保留。异常复核中的重复门禁也通过。
- 当前状态的 1K 三场景及 128K 冷/热门禁未执行；上一轮通过的结果不冒充本轮通过。
- 64-token 样本完成输出和排空，并与旧版核对完整输出 token、forward 大小序列及搬运字节；这不等于每一步都做了独立 FP32/logits 数值门禁。128K 持续运行及引用检查因停止条件未执行。

## 计数与剩余问题定位

测试侧包装计数，不改生产逻辑，不逐块计时。只在 correction、restore、backing、poll 函数边界计时；叶子身份查询和绑定只计数。包装会产生扰动，诊断总时间不进入正式性能表，累计时间含子调用且不能相加。

| 本轮恢复初始需求／收尾访问块数 | — | 962,230 / 52,324 |

全局身份查询仍有 6,937,392 次，不能宣称全部路径只转换一次：本轮只合并同层准备中的重复计算；恢复依赖检查、已有备份与轮询等路径仍调用 canonical 查询。需要继续保留生命周期检查，不能仅为降计数删除。

冷态顺序复核相对旧版的总差距为 +2.731s：TTFT 合计反而减少约 0.159s，排空合计减少约 0.018s；首 token 后执行区间合计增加约 2.908s。因此持续执行差距不能归咎于冷态首窗错位或最后排空。

诊断中两个冷态单请求各 1792 次 correction／backing：correction 累计约 6.53/6.66s（含 restore 3.28/3.35s），backing 约 8.69/8.82s，H2D 全表轮询约 2.23/2.44s。热态 batch correction 14.31s（含 restore 7.79s）、backing 15.60s、轮询 5.47s。这证明还有可观 CPU 成本，但包装及旧 profile 采集方法不同，不能用这些累计时间精确解释正式样本的 2.731s 差距，也不能断言全部来自 D2H 或 poll。未修改这些范围外逻辑。

长输出比较中 token、forward 大小序列、H2D/D2H/SSD 字节保持一致；详见 `output64_comparison.json`。此次已确认的主要问题是重复管理调用，不是减少了实际 Attention 数据。

本轮计数诊断未包装 Attention 算子入口；`attention_compact_calls=0` 是该现有统计未在紧凑入口递增，不能据此认定没有执行 Attention。V100 backend 独立 probe 另核对每次一次写 KV、一次 Attention；真实 64-token 算子总调用数没有作为本轮已测值报告。
