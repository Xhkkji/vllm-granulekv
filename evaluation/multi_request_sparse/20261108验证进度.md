## 已定位的阻塞

**1. bounded GPU slots 的 admission 仍强制单请求。**

`vllm/core/block_manager.py` 的 `can_allocate()` 和 `can_reserve_granulekv_prefix_restore()` 在 bounded 分支中仍执行：

```python
return AllocStatus.LATER if self.block_tables else AllocStatus.OK
```

因此已有请求建立 table 后，第二请求不能准入。r7 的真实 forward 与此一致。后续需要在保留 CPU 总容量、GPU working-set、owner 和 fence 约束的前提下修改 admission，不能仅移除检查或把请求顺序执行当作修复。

**2. 同 prefix 的 sparse plan 被第一个恢复请求消费。**

`vllm/core/async_kv_scheduler.py::_maybe_start_granulekv_prefix_restore()` 在 enqueue 后调用 `_sparse_restore_plans.pop(page_index_key, None)`。r7 日志明确显示：

```text
batch-0: selector=solidattention_dynamic, dynamic_restore=true, destination=mixed
batch-1: selector=dense, dynamic_restore=false, destination=gpu
```

第二请求随后在 `SolidAttentionPolicy.select_actual_blocks_device()` 抛出：

```text
RuntimeError: history selection lacks complete prefix metadata
```

static plan/metadata 准备已使两个独立参考正常完成，因此这次双请求失败不能归为设备权限问题。

**3. 真正同批后的风险仍未验证。**

交接所列 `_restore_live_backing()` 对整个 batch 查询 prediction state、多 prefill/mixed batch、每请求物理 mapping、LOADING 层范围、混合完成与 abort 生命周期，均不能因为当前顺序参考通过就认为已解决。本轮未修改这些生产路径。
