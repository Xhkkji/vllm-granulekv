## V100 算子预验证

V100S、SM70，FP16，28 query heads / 4 KV heads，head size=128、block=16。普通 PagedAttention V1/V2 已实测，与 selected 算子及独立 FP32 对照均在 rtol=atol=0.02 内通过。覆盖不同有效长度、共享历史、私有尾块、请求反序、V1/V2 选择边界及原生 paired-stride KV 布局。

原始五组紧凑长度为 `[33,23]`、`[512,487]`、`[513,503]`、`[8192,8167]`、`[8193,8183]`。单独 batched kernel 比两次 selected 调用更快，但 GPU gather/逐行建表会吃掉收益。直接从 CPU 请求映射构造紧凑表时，准备加计算约 62–187 μs；对照包含完整 8193 项逻辑表构造时约 1903–1963 μs。此为微基准，不外推端到端收益；event span 包括 Python enqueue 间隙，不等于 profiler 的纯 kernel 时间。

## 冷态错位诊断

32K 冷态时间线中，两个首窗 native 提交约为 133.64 ms 和 167.04 ms；后者只剩私有尾块读取。A 在约 209.64 ms 接纳，213.23 ms 的 schedule 仍仅含 A；B 的私有 native 数据首次被观察到 READY 约在 244.07 ms，位于 A 的 forward 期间。此前 Worker 的事件回收没有留下已生成但未返回的 READY。

## slot 阻塞定位与边界

现有 `_reserve_gpu_slots` 在候选共享条目仍含其他请求引用时，直接禁止回收；这些引用表示请求曾绑定过该副本，并不等于本次实际选集仍需要它。长 decode 的历史共享绑定累积，可能把暂时复用变成请求整个生命周期的占用。

CPU 最小复现已确认：容量3，当前各请求实际需求的 canonical 并集也为3；另有一个本步双方均不再需要的旧共享块。它已经 READY、CPU backing 完整、无在途 DMA、使用 fence 已结束，但因仍有 A/B 共享引用，预留新块仍报同一错误。证据为 `reproduce_shared_pin.py/json`。这证明淘汰条件存在额外限制，但真实128K具体占用分类以独立诊断为准。

归档基线的真实诊断已复现同一输出进度（A/B=22/21 token），失败在第26层：

| --- | ---: |
| 物理容量 / 已占用slot | 2135 / 2135 |
| A当前必需逻辑块 / 已有对应映射 / 尚缺 | 501 / 493 / 8 |
| A请求映射总数 | 2123 |
| B请求映射总数 | 2114 |

1630个条目均存在其他请求引用，状态不是PENDING，且没有其他请求已登记的当前需求；采样条目为READY。**但B尚未完成本层实际选块，因此502个已登记canonical需求不是本层两请求最终需求并集**，不能据此把1630个条目直接释放。现有代码在逐请求选择阶段遇到容量压力，而共享引用仍保留历史绑定，缺少以整批当前需求为依据的安全退役步骤。

实际结果与CPU最小复现一致：问题落在共享副本回收条件，不是V100的PagedAttention算子不支持，也不是数值门禁不通过。最小修正方向应为：先选完当前batch并登记全部必需身份，再沿已有解绑路径退役本批不再需要的历史绑定；仅在没有实际消费者、DMA或使用fence保护后复用slot。不能把`shared.references - {request_id}`简单删除，也不能只看尚未更新完整的`required`集合。

本轮遵守异常停止条件，没有直接删除引用、扩大容量或修改淘汰语义来绕过失败。下一步应在本次需求登记与原共享解绑位置研究如何区分“本步仍需保留”与“历史绑定已可退役”，同时保留 DMA、owner、generation 和 fence 检查；先固化真实失败，再决定最小修正。
