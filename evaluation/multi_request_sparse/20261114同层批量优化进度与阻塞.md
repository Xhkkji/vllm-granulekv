## slot 阻塞定位与边界

现有 `_reserve_gpu_slots` 在候选共享条目仍含其他请求引用时，直接禁止回收；这些引用表示请求曾绑定过该副本，并不等于本次实际选集仍需要它。长 decode 的历史共享绑定累积，可能把暂时复用变成请求整个生命周期的占用。

CPU 最小复现已确认：容量3，当前各请求实际需求的 canonical 并集也为3；另有一个本步双方均不再需要的旧共享块。它已经 READY、CPU backing 完整、无在途 DMA、使用 fence 已结束，但因仍有 A/B 共享引用，预留新块仍报同一错误。证据为 `reproduce_shared_pin.py/json`。这证明淘汰条件存在额外限制，但真实128K具体占用分类以独立诊断为准。

归档基线的真实诊断已复现同一输出进度（A/B=22/21 token），失败在第26层：

| --- | ---: |
| 物理容量 / 已占用slot | 2135 / 2135 |
| A当前必需逻辑块 / 已有对应映射 / 尚缺 | 501 / 493 / 8 |
| A请求映射总数 | 2123 |
| B请求映射总数 | 2114 |

1630个条目均存在其他请求引用，状态不是PENDING，且没有其他请求已登记的当前需求；采样条目为READY。**但B尚未完成本层实际选块，因此502个已登记canonical需求不是本层两请求最终需求并集**，不能据此把1630个条目直接释放。现有代码在逐请求选择阶段遇到容量压力，而共享引用仍保留历史绑定，缺少以整批当前需求为依据的安全退役步骤。

实际结果与CPU最小复现一致：问题落在共享副本回收条件，不是V100的PagedAttention算子不支持，也不是数值门禁不通过。最小修正方向应为：先选完当前batch并登记全部必需身份，再沿已有解绑路径退役本批不再需要的历史绑定；仅在没有实际消费者、DMA或使用fence保护后复用slot。不能把`shared.references - {request_id}`简单删除，也不能只看尚未更新完整的`required`集合。

本轮遵守异常停止条件，没有直接删除引用、扩大容量或修改淘汰语义来绕过失败。下一步应在本次需求登记与原共享解绑位置研究如何区分“本步仍需保留”与“历史绑定已可退役”，同时保留 DMA、owner、generation 和 fence 检查；先固化真实失败，再决定最小修正。

### 首次失败的确定原因

`gate_1k_same_cold/summary.json` 保留完整 traceback。populate 已完成两 token；`reference-0-0` 完成 `/0` 末 token 重算并产生首 token 576，进入第二次 forward 时在历史选块处报 `history representative was not sealed before GPU reuse`。这不是选集或 logits 比较不通过，而是生产状态推进异常，门禁尚未完成。

新 `XFormersImpl.forward` 在紧凑入口直接返回 `_forward_compact_sparse` 的结果，跳过原函数尾部的 `update_history_representatives`。对1024-token `/0`：第一次 query 在逻辑位置1023，选块前有63个完整历史块；该次 KV 写入后，私有重算尾块63已完整，应将请求级代表向量封存到64块。新路径没有执行这一步，下一次位置1024的 query 要求64个完整历史块，而缓存仍是63，触发原保护检查。

`reproduce_missing_seal.py/json` 在不启动模型、SSD 或 scheduler 的情况下复现相同错误：实际紧凑 backend 输出为有限值，代表向量数量仍为63；下一次选块失败。诊断脚本单独调用现有封存函数后数量变为64，同一次选块通过。该调用只用于定位，没有写入生产代码，也没有跳过保护、修改评分或更换参考选集。

这同时说明15组单次 Attention 数值检查没有覆盖跨步元数据生命周期，不能替代真实模型门禁。该缺口位于备份检查点已有的紧凑提前返回分支；本轮真实验证首次揭示它。

诊断总耗时121.765s，明显受cProfile和逐层断言扰动；上述时间包含子调用，不能相加，也不能直接扣算正式样本收益。GPU event span包含发射间隙，不是纯kernel时间。测试包装自身产生约375万次身份查询，不能把它们算作生产开销；调用来源已保存在profile摘要中。

已确认的生产重复工作位置：

1. `_correct_bounded_batch` 已算过整批身份集合，随后对每请求调用 `_reserve_gpu_slots` 时又各构造一次同样的整批身份集合；即使有足够空slot也会计算。随后生成new、登记destination时再次转换相同身份。
2. 同一共享READY条目先在整批预绑定处理，再在预留和destination分支处理，恢复结束又对全部历史块调用绑定。诊断中直接来自correction的绑定1350300次、来自restore收尾953718次、reserve452488次；多次写回相同请求映射、resident及引用集合，实际copy需求却很少。正确的阶段约束需要保留，但这些重复登记不需要重复执行。
3. 备份仍对各请求累积resident候选分别做slot/owner/shared检查，之后才按canonical身份合并CPU状态查询和copy；“copy去重”没有消除之前的重复分类。消费者使用fence仍须分别保留，不能简单删除消费者更新。
4. `_poll_host_cache_uses` 仍遍历所有保留的H2D消费记录，绝大多数记录的source lease早已释放。这是当前实测热点，但不能仅凭本轮profile把它全部判成新增退化；当前没有修改其组织或生命周期。

这些证据将问题定位到重复CPU准备工作，而不是普通PagedAttention无法在V100批量执行。下一处最小收敛方向应在现有correction/restore调用内部复用本层临时身份结果、只给新消费者或新副本补绑定，并把容量回收所需集合推迟到实际容量不足时计算；保留现有目录、owner、DMA及fence语义。该进一步优化**本轮未实施**，不新增持久缓存或分支绕过验收。
