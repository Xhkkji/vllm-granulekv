### 5.3 优化链路验收指标

上表是 Figure 13 的 TTFT 口径。由于本次正式请求设置为 `output=2`，同时记录完整请求的 `elapsed_ms`，结果如下：

| Prefix | Dense elapsed (ms) | CPU staging + GPU reuse elapsed (ms) | 相对 Dense |
|---:|---:|---:|---:|
| 16K | 8742.55 | 8847.04 | 慢 1.20% |
| 24K | 5313.50 | 5220.99 | 快 1.74% |
| 28K | 3247.95 | 3168.84 | 快 2.44% |
| 30K | 2151.04 | 2074.77 | 快 3.55% |
| 31K | 1580.17 | 1468.09 | 快 7.09% |
| 32K | 1165.43 | 1365.09 | 慢 17.13% |

因此，统一 runner 下应区分两个结论：

```text
TTFT：六个 prefix 点均有收益，收益范围 0.29%~43.66%；
完整 output=2 elapsed：24K~31K 有 1.74%~7.09% 收益，16K 和 32K 仍有额外开销。
```

32K 没有 suffix，正式请求很快进入 decode；此时 CPU staging 和当前层 host -> GPU 调度成本无法被后续 suffix 计算摊薄。16K 的 SSD/host 恢复工作量较大，也会抵消 rolling overlap 的收益。这个结果说明当前实现已经验证了统一链路和 TTFT 优势，但完整 decode 端到端收益仍依赖 prefix/suffix 比例。

### 5.5 Runner 适配说明

本次统一测试只做了测试层适配，没有修改 GranuleKV native 请求生命周期：

1. working-set 不执行 GPU -> SSD writeback，因此在共同的 32K populate 阶段，通过第二个 decode token 触发 SolidAttention representative 构建，再将 metadata 绑定到每个 prefix 的稳定 page key。
2. `max_tokens=1` 只执行 prefill sample，不会进入独立 decode selector；unmeasured populate 使用至少 2 个 output token，正式测量仍固定为 `output=2`。
3. 每个 prefix 点动态设置精确的 trusted block 数，确保 `16K -> 1024`、`24K -> 1536`，直到 `32K -> 2048` 的 SSD 命中边界正确。
4. 没有引入新的 descriptor pool、completion 协议或额外 SSD 请求；GranuleKV 仍使用原有 `submit/poll/complete` 生命周期。

### 5.6 结论

在统一 Figure 13 runner、统一 manifest、统一 page identity 和统一 metadata preparation 后，CPU staging + GPU residency reuse 路径相对 Dense 在全部六个 prefix 点均取得 TTFT 收益，降低范围为 `0.29%~43.66%`。完整 `output=2` elapsed 在中间 prefix 区间取得 `1.74%~7.09%` 收益，但 16K 和 32K 仍需继续优化。收益主要来自：

```text
SSD 只恢复预测/当前需要的少量 GPU block；
其余 immutable KV 一次性恢复到 host；
当前层需要的 block 优先从 GPU 或 host 复用；
后续 layer window 通过 rolling prefetch 与计算重叠；
event fencing 消除了正常 working-set 回收中的全局 CUDA synchronize。
```

本次结果已经是统一测试口径下的 Dense 对比，不再是此前 Quest runner 与 Tutti Figure 13 runner 混合得到的阶段性结果。后续正式论文数据应同时报告 TTFT 和完整 elapsed，增加重复次数并报告 p50/p95，同时保留本次链路统计作为正确性验收依据。
